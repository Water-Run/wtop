# 国际化与 YAML 语言目录

> 本文档区分当前 `0.1.0` 实现与后续的质量目标。语言目录的稳定/预览标记只描述仓库清单的状态，不代表每种终端与人工语言审校都已完成。

## 1. 当前语言目录状态

`locales/manifest.yml` 当前列出：

- 稳定（stable）：`en-US`、`zh-CN`；
- 预览（preview）：`zh-TW`、`ja-JP`、`ko-KR`、`es-ES`、`fr-FR`、`de-DE`、`pt-BR`、`ru-RU`；
- 计划（planned）：`it-IT`、`pl-PL`、`tr-TR`、`uk-UA`、`id-ID`、`vi-VN`、`th-TH`、`hi-IN`、`ar`、`he-IL`、`fa-IR`。

只有仓库中实际存在、并被纳入生成注册表的语言目录才能作为内置加载。计划中的语言没有内置目录。

稳定/预览的划分描述的是审校成熟度，而不是覆盖面：**目前全部十个内置目录都翻译了每一条消息**，且 `tests/unit/test_i18n_runtime.lua` 对每一个都断言 `missing_messages == 0`，因此新增 UI 字符串而缺翻译会让构建失败。预览目录仍*允许*缺消息——按键回退链对用户自备目录依然存在，而且是用一个故意不完整的目录测试的，不是用内置目录。“预览”在这里的意思是：措辞还没有经过母语者审校。

运行时可用 `L` 切换语言；工作区会重建，因此构造时解析的页面与控件标题会随之更新。

主 TUI、页面与页头、帮助、状态消息和 Inspector 标签现在大量使用消息 ID。常见采集器状态与质量码、传感器来源原因、采集器与检查器失败原因、降级读数原因、进程部分数据原因以及用户语言目录诊断都会在显示层翻译，而 Snapshot 和 JSON 保留原始代码。降级但仍在运行的读数的原因，由选择质量的那同一个表达式选择，因此每个发布的质量恰好对应一个原因和一个代码——CPU 采集器是 `loadavg_unavailable` 和 `cpu_counter_delta_unavailable`，网络采集器是 `default_routes_incomplete` 和 `network_rate_unavailable`。测试断言的是这种配对关系，而不是某个字符串存在与否，因为指错了原因的 reason 是真实目录里的真实代码，任何清单检查都看不见它。单个原因槽位必须通过的测试是：**有一句话在产生该质量的每一种情形下都为真**——网络采集器能通过，磁盘采集器不能，因为它的 `partial` 可能来自调用方的 `include` 谓词抛错，而那根本不是一次部分读取。降级表现为“每个质量一个被测计数器”的采集器走另一种形态：cgroup 采集器读取 `partial_node_count`、`reset_node_count` 和 `gap_node_count`，再无其他，所以它携带**三个**原因；计数器被重置的用户不会被告知“没有可用速率”——重置需要跨它比较计数器，间隙需要第二个样本。传感器采集器是第三种形态：它的两个降级质量是跨所有设备和所有通道取得的计数，而不是各自的一个条件，那句话必须在整个笛卡尔积下成立——`hwmon_data_partial` 对被截断的类枚举、名称溢出文本上限的设备、失败的通道枚举和单个坏通道同样为真；`hwmon_value_derived` 对被替换的平均读数和拼合出的设备身份同样为真，因为这两种情况下屏幕上的数字都不是从传感器读出来的。GPU 采集器是那句话必须靠测量来选定的案例：它的十个 `partial` 原因里有两个是*成功*的读取——DRM 客户端的 `drm-pdev` 指向我们不认识的卡，以及渲染节点不属于任何已枚举的卡——在有意构造之前，套件里没有任何测试产生过这两种情形。“无法读取”对这两种情形为假，所以代码是 `gpu_data_incomplete`，那句话说的是*采集*；被引导去找读取故障的用户会发现每次读取都成功了。它的 `estimated` 一半点名的是实际推断出的东西，`gpu_identity_inferred`：设备身份和节点归属，仅此而已。CPU 信息采集器是同一个测量推翻那句话的案例，而且方向相反：它的 `estimated` 既由取了默认值的 `physical_package_id` 或 `core_id` 置位，**也**由 `/proc/cpuinfo` 未给出 `model name` 和厂商置位，而“某个值是推导而非直接读出”对后一种情形为假，因为缺失的字段不构成对任何东西的推断。所以它的代码是 `cpu_info_value_not_stated`——部分 CPU 信息系统未声明——这对默认值和缺失同样为真，并且指向内核而不是权限。进程采集器的原因表有三行而不是两行，因为它的质量表达式可以返回 `gap`：本样本里没有任何进程有新鲜的 CPU 速率，这根本不是数据降级。`process_rate_unavailable` 就是为此存在的；告诉这类用户“部分进程数据无法采集”，会让他们去追一个不存在的故障。它的 `partial` 一半是 `process_data_partial`。选择该 partial 的四个计数器中有三个在套件产生的 37 个样本里从未触发，所以每一个都是作为样本构造出来的，而不是靠假设——这正是本条反复重学的那条规则的一般形式：从表达式推导出的原因，其受测程度只取决于该表达式的*子句*；没有样本到达的子句，就是没有测试看见的子句。原因表的 `fresh` 行是契约的一部分，不是簿记：它是唯一能与其余两行矛盾的行，而“在整个样本上发布一个原因”这种问题，已经不得不在连续四个增量里靠变异测试抓住。磁盘采集器关闭了该项的最后一部分，而且是靠推翻九个增量前记录的结论关闭的——增量 71 点名的原因全部得到确认，但它当时用一条比标准更强的测试拒绝了它们：它问的是每个原因是否都是*一次失败的读取*，而标准只问*是否有一句话对每个原因都为真*。由于上限同样不是失败的读取，而另外四个已关闭的采集器的 `partial` 桶里也有上限，这条更强的测试差点把整项都关不掉。它的原因是 `disk_data_partial` 和 `disk_rate_unavailable`，而覆盖抛错的 `include` 谓词——`/proc/diskstats` 公布过、结果里却没有的设备——的那句话，说的是*采集*，不是读取。它背后的测量才是值得保留的部分：该采集器**没有自己的测试文件**，整个套件在两处构造它，共产生三个样本，没有一个处于讨论中的质量。靠读代码得出的结论只是假设；对一条记录在案的“不可关闭”，第一件事是去测量它。原因清单现在有了针对整棵树的第三个方向，而正是那次测量关闭了该项：153 个界面代码、37 个仅机器代码，没有交集，且 **153 个中没有一个拼不出来**——每一个仍会被产生，所以目录里没有死翻译。守卫的按位置测试看不见的 33 个代码（它要求字面量与 `reason =` 同行）分成四组，每一组都由那次扫描之外的机制把守：十二个是写在续行上的采集器原因值，各由一条配对断言点名；十一个是工作区与布局代码，在运行时格式化进 `reason.` 消息 ID，并在组装消息 ID 表中声明；九个拼写自原生模块，由原生扫描读取。这十一个的一组才是真正费工的地方，而且它是靠写变异测试发现的：那张表为每个变量声明了一组代码，但没有任何东西把代码组与被调用方实际能返回的值核对，于是新的一种工作区名称拒绝通过了所有子句，以英文 snake_case 到达了十种语言的用户。该子句现在检查另一个方向——在任一模块中拼写、未被任何条目声明的 `interface_reasons` 代码。该规则更宽的版本被测量后否决了：那两个模块返回 52 个代码形态的字面量，而表声明了 13 个，其余 39 个是任何调用方都到不了的参数守卫，按本项目的先例属于 `machine_only`。会对正确代码报警的守卫会渐渐没人读，所以规则限定在今天可满足的方向上；它还带了第二条断言，因为它自己的第一个变异——删掉喂给它的文件读取——曾静默通过。第五个扫描家族覆盖上一个覆盖不了的形态：`Capability` 构造器的第一个位置参数，它会成为 `capability.reason`，并通过 `Technical.reason` 渲染进 Collectors 和 Inspectors 两张表。十一处在这里传代码形态的字面量，六十八处传的是*系统*产生的东西——本项目的边界有意不翻译后者。十一个里有三个不在任何一张清单上，而缺陷最清楚的表述是：它们所在的文件里，自己的同类已被覆盖——`socket_tables_partial` 写在 `reason =` 字段上，有十种翻译；而 `socket_tables_denied` 和 `socket_tables_unavailable` 在它下面十一行、同一个函数里，一种翻译都没有——于是无权读取套接字表的主机，在所有语言里都以英文 snake_case 得到告知。写这个家族还付出了两个值得保留的错误：匹配 `Capability.new` 把它传入的五个*状态*名报成未列出的代码；以及交替分支用 `|` 写进了 Lua 模式——Lua 模式没有交替也没有分组，因此什么都没匹配到。另外，还发现全部十个目录文件里都带着六个乱序的 `reason.*` 键，序列中间还插着十一个 `sampling.*` 键——两者都不会让任何东西失败，而顺序正是读者赖以察觉缺失键的东西——所以两者现在都有断言，并且修复被验证为一次置换：既有键值对全部不变，加上三个新增。那条断言读的是源 YAML 而不是生成的 Lua，因为生成的目录是哈希表，不携带顺序——这也正是跨 libc 容器现在也暂存 `locales/` 的原因：它是暂存清单缺的第五个目录，也是清单自己的注释早已预言到的第二个。守卫还检查两张清单都不重复代码，这条以前没有，直到一个重复溜了进来：同一个代码的两条目既满足目录检查（第一遍有键，第二遍照样有），又满足拼写检查（拼出的代码已入清单），却恰恰是它看起来像达成一致的第二种拼写错误。每个采集器测试都委托的那条配对断言住在 `tests/support/collector_reason.lua` 里，而它本身也在测试之下，因为把三份拷贝抽到一处买到的是可维护性，一点安全性都没买到，直到有东西去读它：把它的函数体替换成无条件 `return` 的变异通过了所有采集器测试，因为没有一个测试检查它返回什么。macOS 与 Windows 的派发器是原因列为空被“保证”而不仅是常见的案例——它在两个平台的每台主机上都发布质量而不发布原因——所以它自带两个类别级原因；给它的七个派生辅助函数各自配上 Linux 对应方发布的原因会更具体，也不需要新词汇，这被记录为开放问题，而不是在派发器里顺手决定。当采集器的降级是独立来源的*列表*时，槽位取的是类别——系统信息采集器是 `system_identity_incomplete`，其 notes 为 `os_release_unreadable` 和 `dmi_denied`/`dmi_unavailable`——而从第一条 note 推导原因的变异会被抓住，因为它断言了一种质量字段从未表达过的优先级。其余技术标识符是 **35 个没有任何渲染表面展示的代码，它们完全不带翻译**——两个准入预算标记（`calls`、`time`）、二十二个只由 JSON 导出携带的逐行标记、九个只从 `data.providers` 读取的厂商库失败，以及两个输入解码器上限（其事件在任何东西渲染之前就被丢弃）。最后一组以前在十种语言里都有翻译，而其原因正是下一段的主题：*不翻译*是一项必须被断言的决定，否则当它不再成立时，永远不会有东西察觉。一个伪语言布局测试会把最长的内置消息在每个必需的宽高比下渲染。

`tests/unit/test_reason_localization.lua` 中的原因清单，靠一条关于**字符串字面量在 `reason =` 值中处于什么位置**的规则与产品相互约束，而不是靠一份“原因都以哪些形态书写”的清单：代码形态的字面量在值开头、或紧跟裸的 `and`、`or` 或 `..` 时是原因；跟在比较运算符后面的字面量是操作数，不是代码。形态清单是最先尝试的，扩了三次，找出**三十四个**正以英文记号到达本地化界面的代码——两个在 `reason = "code"` 里，十七个在 `reason = <fallback> or "code"` 里，十五个在 `reason = <flag> and "code" or nil` 里，也就是产品为所有条件性降级使用的形态。这条规则既对照整棵树测试，也按自身条款测试，因为按形态计数分不清“不再读某个位置”的规则和“什么都不读”的规则：只看计数时，删掉 `and` 子句后套件依然全绿，而十四个代码坐在规则之外。规则读不了的是换行，因此续行到下一行的原因值在它之外；而树上大多数 reason 字段在自己那行没有字面量——透传、来自解析函数的值，以及是句子而不是代码的错误消息。2026-10-02 用规则自己的按位置测试（非局部变量的 `reason =`）在 `src/wtop` 上计数：**260 个 reason 字段，97 个同行带字面量，163 个不带**。这是对既定方法的一次测量，而不是强制阈值，所以会随采集器增加而漂移；它度量的是盲区的大小。其中一句，macOS/Windows 采集器里的 `missing CPU counters`，已被更正为代码 `cpu_counters_missing`：*系统*产生的字符串不是翻译问题，因为它无法枚举；*本项目*写下的字符串是翻译问题，因为它是一组固定的词。

**这条规则还只读了一种语言。**扫描跑在 `src/wtop` 上，而原因并不只用 Lua 书写：`wtop_native.c` 把执行器自身的失败代码赋给局部变量再直接压入结果的 `reason` 字段；`wtop_nvml.c`、`wtop_amdsmi.c` 和 `wtop_levelzero.c` 各把三个代码赋给 GPU 采集器原样拷贝的提供方结构体。测量下来，原生源码里有**五个到达界面的未翻译代码**——`cancelled`、`cancel_callback_failed`、`poll_failed`、`waitid_failed`、`waitpid_failed`——以及**九个只到达 JSON 导出的代码**，因为在整个 Lua 树里只有 `export.lua` 读取 `data.providers`，没有任何视图模型提到它。于是本文件中的两张清单现在是：那五个在十种语言里都有翻译；那九个列为 `machine_only` 并写明理由，因为一个没人看得见的 C 拼写代码，恰恰是最容易悄悄丢失的东西。扫描也读原生源码，按两种测量出的形态——对名字以 `reason` 结尾的东西的赋值，以及在 `lua_setfield(L, -2, "reason")` 前一行压入的字面量——并且每种形态都断言匹配到了东西，因为丢了某一种形态的规则仍会报告其余的。原生扫描不做的，是追踪变量：`lua_pushstring(L, internal_reason)` 经赋值形态解决，而从更远处到达 `reason` 字段的值仍在它之外。

**第三个方向现在有了断言，而它正是缺的那个。**守卫一直检查两件事：产品拼出的每个代码都已入清单；清单里的每个代码都有翻译。它从未检查**清单里的每个代码都是产品仍能产生的**——三件事里只有这一件能抓住改名的代码、删除的分支或丢弃的厂商库，而这三者每一种都会留下十种语言的字符串和一条断言着已不存在之物的清单条目。这项检查是对 `src/` 和 `native/` 的拼写检查：*在某处拼出过*是可检查的，*到达某个展示表面会渲染的 reason 字段*不可检查，两者的距离并不隐藏——它就是 `docs/PLAN.md` 里那条开放项，记录着两次扫描都看不见的二十个清单代码，连同给它们分类的那次测量。那二十个里有一个是“拼写不等于可达”最锋利的例证：`query_denied` 只在 `native/wtop_windows.c` 和一个测试夹具里拼写，它到达的是导出携带而任何视图模型都不读取的 `partial_reason` 字段。

**第七种形态曾被描述为无法看守，而测量它时发现了一个 bug。**到目前为止，本文件的规则读的都是*字面量*，而 `tui.lua` 会用值拼出一个：`translated(translator, "reason." .. tostring(apply_error), ...)`，六处。测量下来有六个这样的位置，都在 `tui.lua`，每个变量由一两个 `workspace:` 调用赋值，其返回值构成词表。追踪其中一个，翻出的不是局限而是真实缺陷：`Workspace:move_focused_to` 未经过滤地返回布局模型的错误字符串，而 `add`、`remove` 和 `replace` 都把自己的错误传过了 `layout_refusal`；`Layout.move` 对不在页面上的目标**拼一个字符串**作答——`"widget_not_found:" .. target_widget`。于是在本机上，`move_focused_to("not_a_widget_on_this_page", "after")` 回答 `widget_not_found:not_a_widget_on_this_page`，状态行拼出消息 ID `reason.widget_not_found:not_a_widget_on_this_page`，没有哪个目录能容纳带冒号的键，`Technical.reason` 回退到原始拼写——在所有语言里。它现在回答 `widget_not_in_page`。教训正是本文件不断以新面目重学的那条：**不可分析的形态不等于不存在的形态**，而去看它的理由是：六个位置已知，却一个都没读过。守卫现在按位置声明词表，连同每个变量被赋值的被调用方，并检查四件事：`src/wtop` 里的每个位置都已声明；文本为某位置显示的每个被调用方都是条目点名的——于是复用旧变量名的新调用没法躲在为旧调用写的条目后面；每个声明的代码都已入清单；每个声明的变量仍有位置。位置读取器会先剥掉 `--` 注释，这是承重而非整洁：这个 bug 的修复紧挨着它所改的那一行上方，并引用了它移除的表达式，按原始行扫描会在 `workspace.lua` 里报出第七个位置并拒绝该修复。这条规则仍然做不到的，是把声明的词表与被调用方核对——那是本文件不做的跨过程分析，所以词表是一个主张，清单是它唯一可能的反驳。

**同时出现在两张清单里的代码就是那个洞，现在已闭合。**上面那二十个已分类，而分类系于注释里的一个词：清单的范围写的是“状态行、部分行标记或检查器浮层”，而进程行上的 `partial_reason` *就是*部分行标记，于是那条注释把二十二个导出代码放进了表头写着“只有展示层本地化”的清单。这一歧义由产品自己的先例而非偏好解决——`budget_reason = "calls"`/`"time"` 一直是 `machine_only`，经同类逐行字段进入 agent 载荷，从来没有目录条目——所以那二十二个并入它，**240 条目录条目被删除**，每个内置目录的 `reason.*` 键从 154 降到 130。核对分类又翻出了这些条目之所以能删这么久的原因：`input_buffer_limit` 和 `input_sequence_limit` 既在 `interface_reasons` 里，也在 `machine_only` 里。同时在两张清单里的代码不是重复，而是守卫看不见的矛盾——翻译检查问界面清单，拼写检查问并集，两边的条目通过一切检查，而关于它的两句话互相矛盾。测量下来，界面那边是错的：两个代码都以 `{type = "error"}` 事件到达，`process_event` 没有 `event.type == "error"` 的分支，`event.reason` 在 `tui.lua` 里出现零次，两个非按键直落分支都 `return`，于是事件被丢弃，代码从不渲染。它们的二十条翻译是什么都显示不了的字符串。守卫现在断言四件以前不断言的事：两张清单不相交；每个 `machine_only` 条目带非空的证据字符串（以前有四个条目是光秃秃的 `true`，该豁免现已移除）；**`machine_only` 代码不得携带 `reason.*` 键**——旧规则是 `not known[code] and not machine_only[code]`，这样的代码携带键时它*通过*，于是“仅机器”曾是留着一条翻译不动的理由；以及上述三种失败模式各自在真实 `en-US` 目录的拷贝上探测，距内置文件一步之遥的一次插入或删除——因为仅仅“长得像”的合成夹具证明力更弱。

## 2. 源文件与运行时结构

```text
locales/
  manifest.yml
  _template.yml
  en-US.yml
  zh-CN.yml
  ...
src/wtop/i18n/
  init.lua
  catalog.lua
  format.lua
  locale.lua
  plural.lua
  technical.lua
  user_catalogs.lua
  yaml_profile.lua
src/wtop/generated/locales/
  registry.lua
  en-US.lua
  zh-CN.lua
  ...
```

`locales/*.yml` 是内置翻译的人工可编辑权威来源。`src/wtop/generated/locales/*.lua` 是确定性的构建产物，不得手工编辑。打包产物使用生成的 Lua 模块作为内置目录，启动时不解析内置 YAML。

## 3. 语言目录 Schema

```yaml
_meta:
  locale: "en-US"
  name: "English (United States)"
  direction: "ltr"
  fallback:
    - "en"
  plural_rule: "en"
  catalog_version: 1

messages:
  app.title: "wtop"
  tabs.overview: "Overview"
  process.count:
    one: "{count} process"
    other: "{count} processes"
```

受限的 YAML 方言与目录校验目前强制以下规则：

- 只允许一个 UTF-8 文档，且仅含受限的映射、序列和标量形式；
- 禁止锚点、别名、合并键、自定义标签和重复键；
- 根节点只接受 `_meta` 和 `messages`，未知的 `_meta` 字段会被拒绝；
- 目录的 `_meta.locale` 与回退 locale 必须是规范化的 BCP 47 标签，消息 ID 使用小写点分隔路径；
- 文本参数使用 `{name}`，同一条复数消息的每个分支必须使用相同的占位符；
- 复数类别必须为所选规则所允许，并包含该规则要求的全部分支；
- 稳定的内置目录必须与 `en-US` 完全兼容；预览目录可以缺消息，但其定义的每条消息必须有兼容的结构和占位符。

解析器不是通用的 YAML 执行环境，既不构造对象也不执行标签。

## 4. 构建

```bash
make locales

.tools/lua-5.5.1/bin/lua tools/compile_locales.lua \
  --source locales \
  --output src/wtop/generated/locales \
  --check
```

编译器校验清单与目录的一致性，按 locale 和消息 ID 排序确定性地生成 Lua 模块，记录源 SHA-256、目录版本和生成器版本，并输出一个使用字面 `require` 调用的注册表。`--check` 把期望输出与已提交的生成产物比较。

当前的编译门槛不包括人工语言审校、截图对比、伪语言扩展或在多种终端里的 RTL 测试。这些仍是发布流程的工作。

## 5. 用户 XDG 语言目录

启动时，TUI 自动扫描：

```text
$XDG_CONFIG_HOME/wtop/locales/*.yml
```

`XDG_CONFIG_HOME` 未设置时，使用 `~/.config/wtop/locales/*.yml`。当前上限是 64 个候选文件、每个 1 MiB。文件名必须安全并以 `.yml` 结尾。目录不存在是正常的缺失状态。

用户语言目录通过与内置目录相同的解析器/schema 校验和 `en-US` 兼容性检查，但可以不完整。文件按名称顺序加载。重复的 locale、不安全的文件名、读取失败、超限文件和校验失败分别记录，其余安全文件继续加载。TUI 目前只在底部状态区显示已加载/出错的计数或第一个失败原因；没有语言目录管理页，也没有完整的错误列表。

用户语言目录不进入 onedir/onefile 载荷，也不修改仓库的内置注册表。用户目录可以覆盖同一 locale 的内置目录；缺失的键仍走回退链。

CLI 和主配置不要求请求的标签已存在于内置注册表。它们先校验并规范化 locale 语法，允许合法的未知标签进入 TUI。创建翻译器之后，加载用户语言目录会按原始请求重建回退链，因此 `$XDG_CONFIG_HOME/wtop/locales/*.yml` 可以为该标签提供实际翻译。`--snapshot` 和 `--diagnose` 不创建翻译器，也不扫描用户目录。

## 6. 语言选择与回退

请求语言的优先级是：

```text
--lang > config locale > LC_ALL > LC_MESSAGES > LANG > en-US
```

规范化示例：

```text
zh_CN.UTF-8 → zh-CN
pt_BR       → pt-BR
```

规范化处理 `_`、字母大小写和常见的环境后缀。空子标签、非法字符、重复的 variant/extension、缺失的 extension 值这类语法错误，会被 `--lang` 或配置校验拒绝。合法但未知的规范化标签不会被 CLI 当作拼写错误。TUI 加载后，如果用户目录和内置目录都不存在，解析会沿父标签/别名回退，最后落到 `en-US`。用户语言目录的 `_meta.locale` 必须已是规范化形式；加载不会改写它。

Translator 先解析最佳匹配的已加载目录，递归应用其 `_meta.fallback`，最后加上 `en-US`。例如当前 `zh-TW` 的链是 `zh-TW → zh-CN → en-US`。回退按消息 ID 逐条发生。查不到时返回 ID 并递增内部诊断计数器，不会终止整个 TUI。

Translator API 能报告请求与实际使用的 locale、书写方向、回退链、覆盖率、缺失计数、格式化错误及其他诊断。Insights 页面和 `--diagnose` 尚未暴露这整套信息。

## 7. 复数与格式化

当前实现内置复数规则，使用 `zero`、`one`、`two`、`few`、`many`、`other` 的按语言子集。格式化器提供：

- 按语言区域的小数分隔符与分组，目前只给部分语言定义了惯例；
- SI/IEC 字节、bit/s、频率、时长、百分比以及摄氏/华氏温度；
- 具名占位符插值。

这不是完整的 CLDR/ICU 实现。缺少日期/时间与时区格式化、货币、排序规则、复杂消息格式、度量系统的自动选择，以及每种语言的本地数字符号。部分 TUI 文本仍直接拼接技术字段。

## 8. Unicode 与 RTL 边界

渲染器按终端单元格测量 UTF-8、CJK、组合字符、emoji 和变体选择符，并优先使用原生 `wcwidth`。真实终端宽度表之间的差异仍可能造成个别的对齐问题。

目录 schema 接受 `_meta.direction: "rtl"`，Translator 也能返回书写方向。但工作区、表格、按键绑定和渲染器尚未用它做镜像、bidi 隔离或整形，仓库也没有内置 RTL 语言目录。因此 RTL 是可表达的元数据，不是受支持的 UI 能力；倒转字符串不是可接受的替代。

## 9. 渲染闭包

上面的原因清单是一次**字面量**扫描：它读 `reason =` 位置、`Capability` 构造器的第一个参数和原生源码，问的是产品*拼出*什么。状态与质量标签还有第三个问题，上述哪一个都问不了，而 2026-10-02 那天，里面正坐着一个缺陷。

`i18n/technical.lua` 是技术标签到达屏幕的唯一路径。`Technical.state(i18n, value)` 查 `status.<value>`，`Technical.reason` 查 `reason.<value>`，两者在键缺失时都**回退到原始参数**——在所有语言里同时、无声地。没有标签的值因此不是崩溃也不是日志行；它是日语或俄语界面里的英文 snake_case，而构建中没有任何东西察觉。

找到了两个这样的值，在产生它们的源码里哪个都不是字面量：

- `missing`——挂载点的质量是 `statvfs_error` 的分类器返回的任何值，由 `mounts.lua` 携带、经 `view_model.lua` 进入 I/O 页的 Quality 列；
- `held`——GPU 引擎的速率质量是 `current_ns < old_high and "held"`，一次与上一样本的比较，浮层把它印在它所限定的数字旁边。

`tests/unit/test_state_render_closure.lua` 用运行渲染器的方式回答第三个问题。它替换 `Technical` 的两个字段，驱动全部八个标签页的每张表模型、GPU 客户端浮层，以及产生那两个非字面量值的两个采集器，然后断言：渲染器查过的每个值在全部十个目录里都有标签；十三个已发布质量的每一个都有；词表旁边的严重度排序到达使用它的那一列。测量下来，驱动记录了**七个不同的状态值**；这个数字被断言，于是驱动无法悄悄不再到达渲染器、报告一个干净、空而“真实”的结果。

本项目语言目录的两个性质，决定了守卫必须说什么。

**`en-US` 是参照。**构建翻译器时，`i18n/catalog.lua` 用它校验其他每个编译后的目录，于是 `en-US` 缺键在 `I18n.new` 处抛错，任何单独一种语言缺键也是加载期错误。*全部十种*都缺的键则自洽、干净地加载，直落到原始拼写。这是这种 bug 唯一无声的形态，也是两次全量目录扫描都一无所获的原因。守卫因此检查*生成的*目录——那才是渲染器读的东西——而第六条子句检查 YAML 源，因为加进了生成模块、忘在 `locales/*.yml` 里的键，是下一次 `make locales` 会删掉的键。

**对非代码值，直通是有意为之。**`localized` 只在值匹配 `^[a-z][a-z0-9_]*$` 时才查表；其余原样返回。视图模型放进空 Quality 单元格的破折号占位符按构造就是语言中立的，守卫用渲染器自己的判据而不是另造一个——给被守护的代码发明更严的测试，正是增量 80 拒绝正确答案的方式。

**存在却显示不出的标签，是同一缺陷换了一顶帽子。**`ui/widgets/table.lua` 把每个单元格截断到列宽，而渲染状态的各列是按英文词定宽的：`Unavailable` 占 11 格，最宽的列只有 10。跨全部十个目录测量，最长的标签是法语的 *Échantillon manquant*（`gap`）占 20 格，五个超过 13。于是读着被拒绝采集器的德国用户看到的是 *Nicht verf…*——不是翻译，不是代码，也没有错误，因为截断本来就是渲染器的日常行为。

修复是把八列放宽到 `STATE_COLUMN_WIDTH = 20`，而让这个数字安全的是机制而不是愿望：一列凭其 `min_width` *被纳入*，声明的 `width` 只是渲染器朝它生长的偏好，于是抬高偏好不会挤掉别的列的席位。在 PTY 矩阵用的八种终端尺寸上测量，64 个（列，尺寸）对里有 22 个发生变化，且没有任何表在任何地方丢列；不变的 42 个是那些列已处于最小宽度、无论如何都会被裁的尺寸。`min_width` 有意未动——抬高它会让列在窄终端上消失，那比短单元格更糟。**备选方案是缩短翻译**——那样保住了列，却用装得下的缩写替换了正确的德语、西班牙语和法语词。守卫条款现在按状态列*做什么*而不是按名单识别它们，于是第九个这样的列无需任何人记得添加也被覆盖。

## 10. 剩余发布门槛

- 从核心可见文本中移除硬编码回退与未翻译的提供方原因，或显式定义技术字段例外。
- 为稳定语言目录指定维护者并记录人工审校，包括占位符上下文而不只是结构。
- 增加长文本/伪语言与多尺寸截图或金样回归；仓库目前没有 `_pseudo.yml`。
- 在宣称支持 RTL 之前，先实现方向性布局、bidi/整形策略和终端矩阵。
- 为用户语言目录提供可访问的详细错误报告以及覆盖/回退诊断。
- 定义稳定覆盖、截图尺寸与晋升流程，并让 CI 执行这些门槛。
