# Internationalization and YAML Catalogs

> This document distinguishes the current `0.1.0-dev` implementation from later quality goals. A catalog's stable or preview designation describes repository manifest state only; it does not mean that every terminal and human-language review has been completed.

## 1. Current Catalog Status

`locales/manifest.yml` currently lists:

- stable: `en-US`, `zh-CN`;
- preview: `zh-TW`, `ja-JP`, `ko-KR`, `es-ES`, `fr-FR`, `de-DE`, `pt-BR`, `ru-RU`;
- planned: `it-IT`, `pl-PL`, `tr-TR`, `uk-UA`, `id-ID`, `vi-VN`, `th-TH`, `hi-IN`, `ar`, `he-IL`, `fa-IR`.

Only catalogs that exist in the repository and are included in the generated
registry can be loaded as built-ins. Planned catalogs have no built-in catalog.

The stable/preview split describes review maturity, not coverage: **all ten
shipped catalogs currently translate every message**, and `tests/unit/
test_i18n_runtime.lua` asserts `missing_messages == 0` for each of them, so a UI
string added without a translation fails the build. Preview catalogs are still
*permitted* to omit messages — the per-key fallback chain remains in place for
user-supplied catalogs, and is tested against a deliberately partial catalog
rather than against a shipped one. What "preview" means here is that the
wording has not been through a native-speaker review pass.

The language can be changed at runtime with `L`; the workspace is rebuilt so
page and widget titles, which are resolved at construction, follow.

The main TUI, pages and headers, help, status messages, and Inspector labels now use message IDs extensively. Raw kernel/provider fields, status/quality/reason values, and some diagnostic text remain technical English identifiers; i18n coverage is not yet complete.

## 2. Source and Runtime Structure

```text
locales/
  manifest.yml
  _template.yml
  en-US.yml
  zh-CN.yml
  ...
src/wtop/i18n/
  init.lua
  catalog.lua
  format.lua
  locale.lua
  plural.lua
  user_catalogs.lua
  yaml_profile.lua
src/wtop/generated/locales/
  registry.lua
  en-US.lua
  zh-CN.lua
  ...
```

`locales/*.yml` files are the human-editable authoritative source for built-in translations. `src/wtop/generated/locales/*.lua` files are deterministic build artifacts and must not be edited by hand. Bundles use the generated Lua modules for built-in catalogs and do not parse built-in YAML at startup.

## 3. Catalog Schema

```yaml
_meta:
  locale: "en-US"
  name: "English (United States)"
  direction: "ltr"
  fallback:
    - "en"
  plural_rule: "en"
  catalog_version: 1

messages:
  app.title: "wtop"
  tabs.overview: "Overview"
  process.count:
    one: "{count} process"
    other: "{count} processes"
```

The restricted YAML profile and catalog validation currently enforce the following:

- one UTF-8 document containing only the restricted mapping, sequence, and scalar forms;
- anchors, aliases, merge keys, custom tags, and duplicate keys are forbidden;
- the root accepts only `_meta` and `messages`, and unknown `_meta` fields are rejected;
- catalog `_meta.locale` and fallback locales must be normalized BCP 47 tags, while message IDs use lowercase dot-separated paths;
- text parameters use `{name}`, and every branch of the same plural message must use identical placeholders;
- plural categories must be permitted by the selected rule and include all branches required by that rule;
- stable built-in catalogs must be fully compatible with `en-US`; preview catalogs may omit messages, but any message they do define must have a compatible structure and placeholders.

The parser is not a general-purpose YAML execution environment. It neither constructs objects nor executes tags.

## 4. Build

```bash
make locales

.tools/lua-5.5.1/bin/lua tools/compile_locales.lua \
  --source locales \
  --output src/wtop/generated/locales \
  --check
```

The compiler validates manifest/catalog consistency, deterministically generates Lua modules sorted by locale and message ID, records the source SHA-256, catalog version, and generator version, and emits a registry that uses literal `require` calls. `--check` compares expected output with the committed generated artifacts.

Current compilation gates do not include human language review, screenshot comparison, pseudolocale expansion, or RTL testing in multiple terminals. Those remain release-process tasks.

## 5. User XDG Catalogs

At startup, the TUI automatically scans:

```text
$XDG_CONFIG_HOME/wtop/locales/*.yml
```

When `XDG_CONFIG_HOME` is unset, it uses `~/.config/wtop/locales/*.yml`. Current limits are 64 candidate files and 1 MiB per file. Filenames must be safe and end in `.yml`. A missing directory is a normal absent state.

User catalogs pass through the same parser/schema validation and `en-US` compatibility checks as built-in catalogs, but may be incomplete. Files are loaded in name order. Duplicate locales, unsafe filenames, read failures, oversized files, and validation failures are recorded separately while other safe files continue loading. The TUI currently shows only the loaded/error counts or the first failure reason in the bottom status area; it has no catalog management page or complete error list.

User catalogs are not included in the onedir/onefile payload and do not modify the repository's built-in registry. A user catalog may override the built-in catalog for the same locale; missing keys still follow the fallback chain.

The CLI and primary configuration do not require a requested tag to exist in the built-in registry. They first validate and normalize locale syntax, allowing valid unknown tags into the TUI. After the translator is created, loading user catalogs rebuilds the fallback chain for the original request, so `$XDG_CONFIG_HOME/wtop/locales/*.yml` can provide actual translations for that tag. `--snapshot` and `--diagnose` do not create a translator or scan the user directory.

## 6. Language Selection and Fallback

Requested-language precedence is:

```text
--lang > config locale > LC_ALL > LC_MESSAGES > LANG > en-US
```

Normalization examples:

```text
zh_CN.UTF-8 → zh-CN
pt_BR       → pt-BR
```

Normalization handles `_`, letter case, and common environment suffixes. Syntax errors such as empty subtags, illegal characters, duplicate variants/extensions, or missing extension values are rejected by `--lang` or configuration validation. A valid but unknown normalized tag is not treated as a typo by the CLI. If neither a user nor built-in catalog exists after the TUI loads, resolution falls back through parent tags/aliases and then `en-US`. A user catalog's `_meta.locale` must already use normalized form; loading will not rewrite it.

The Translator first resolves the best-matching loaded catalog, recursively applies its `_meta.fallback`, and finally adds `en-US`. For example, the current `zh-TW` chain is `zh-TW → zh-CN → en-US`. Fallback occurs per message ID. A missing lookup returns the ID and increments an internal diagnostics counter without terminating the entire TUI.

The Translator API can report the requested and active locales, direction, fallback chain, coverage, missing count, formatting errors, and other diagnostics. The Insights page and `--diagnose` do not yet expose this complete set.

## 7. Plurals and Formatting

The current implementation contains built-in plural rules using the language-specific subsets of `zero`, `one`, `two`, `few`, `many`, and `other`. The formatter provides:

- locale-aware decimal separators and grouping, with conventions currently defined for only some languages;
- SI/IEC bytes, bit/s, frequency, duration, percent, and Celsius/Fahrenheit;
- named-placeholder interpolation.

This is not a complete CLDR/ICU implementation. It lacks date/time and time-zone formatting, currency, collation, complex message formats, automatic measurement-system selection, and local numeral symbols for every locale. Some TUI text still directly combines technical fields.

## 8. Unicode and RTL Boundaries

The renderer measures UTF-8, CJK, combining characters, emoji, and variation selectors in terminal cells and prefers native `wcwidth`. Differences between real terminal width tables can still cause isolated alignment problems.

The catalog schema accepts `_meta.direction: "rtl"`, and the Translator can return the direction. However, Workspace, tables, key bindings, and the renderer do not yet use it for mirroring, bidi isolation, or shaping. The repository also has no built-in RTL catalog. RTL is therefore expressible metadata, not a supported UI capability; reversing strings is not an acceptable substitute.

## 9. Remaining Release Gates

- Remove hard-coded fallbacks and untranslated provider reasons from core visible text, or explicitly define technical-field exceptions.
- Assign maintainers and record human reviews for stable catalogs, including placeholder context rather than structure alone.
- Add long-text/pseudolocale and multi-size screenshot or golden regressions; the repository currently has no `_pseudo.yml`.
- Implement directional layout, bidi/shaping strategy, and a terminal matrix before claiming RTL support.
- Provide accessible detailed error reports plus coverage/fallback diagnostics for user catalogs.
- Define stable-coverage, screenshot-size, and promotion processes, and make CI execute those gates.
